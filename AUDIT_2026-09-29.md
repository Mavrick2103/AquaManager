# Audit technique AquaManager — 29 septembre 2026

## Périmètre et verdict

Audit local du code présent, y compris les modifications non commitées. Aucun code applicatif corrigé. Revue ciblée de l'architecture, de l'authentification, des accès aux aquariums, de la validation, du frontend et du déploiement. Ce rapport ne constitue pas un audit exhaustif ni un test d'intrusion du serveur de production.

Le projet compile et ses tests passent, mais plusieurs défauts de contrôle d'accès et de gestion des sessions doivent être corrigés en priorité.

## Contenu du projet

- Frontend Angular 20, composants Material, graphiques Chart.js, rendu serveur des pages publiques.
- API NestJS 11, TypeORM et MySQL ; authentification JWT, rôles USER/EDITOR/ADMIN et droits par abonnement.
- Fonctionnalités : aquariums, poissons/plantes, mesures d'eau, calendrier et rappels, recommandations, gamification, articles et fiches espèces.
- Services externes : paiements Stripe/PayPal, SMTP, analyses IA, génération marketing et Instagram.
- Infrastructure : Docker Compose, Nginx, certificats Let's Encrypt et workflows GitHub Actions.

## Constats prioritaires

### 1. P1 — Accès aux poissons/plantes des autres utilisateurs

Preuve : `back_end/src/catalog/aquarium-card-pivot/aquarium-items.controller.ts:33`, `:65`, `:88`, `:102`, `:126`, `:149`. Le contrôleur est bien enregistré dans `AquariumsModule`.

Les six routes GET/POST/DELETE utilisent uniquement l'identifiant d'aquarium fourni dans l'URL. Elles ne récupèrent pas l'utilisateur connecté et ne contrôlent pas le propriétaire. Les guards globaux vérifient l'authentification, mais n'ajoutent aucun contrôle de propriété.

Conséquence : un utilisateur authentifié connaissant l'identifiant d'un autre aquarium peut consulter, ajouter/remplacer les quantités et supprimer ses associations poissons/plantes.

Correction : vérifier le couple aquarium/utilisateur avant chaque opération, idéalement dans un service partagé. Ajouter des tests HTTP avec deux propriétaires distincts pour les six routes. Constat statique ; aucune donnée réelle d'un autre compte n'a été consultée ou modifiée.

### 2. P1 — Jetons d'accès et de renouvellement interchangeables

Preuve : `back_end/src/auth/auth.service.ts:117-128`, `back_end/src/auth/jwt.strategy.ts:14-24` et `back_end/src/auth/auth.module.ts`.

Les deux jetons utilisent la même signature et le même contenu, sans type ou audience contrôlé. La différence est seulement leur expiration. La vérification locale sur le code compilé confirme les deux directions : access vers refresh et refresh vers Bearer.

Conséquence : un jeton d'accès compromis peut être soumis comme cookie refresh pour obtenir une session longue ; un refresh compromis est utilisable directement sur les routes API.

Correction : distinguer explicitement les usages par des claims vérifiés, avec audiences et/ou clés séparées. Refuser systématiquement le mauvais type et ajouter des tests de non-interchangeabilité.

### 3. P1 — Sessions non révocables et rôles périmés conservés

Preuve : `back_end/src/auth/auth.controller.ts:53-56`, `back_end/src/auth/jwt.strategy.ts:21-25`, `back_end/src/users/users.service.ts:162` et méthode `resetPasswordByTokenHash`.

Le refresh reprend directement le rôle du jeton sans consulter l'utilisateur en base. Aucun état de session n'est invalidé après changement de mot de passe, suppression de compte ou changement de rôle. Logout efface seulement le cookie du navigateur ; l'ancien refresh reste valable côté serveur jusqu'à son expiration et permet d'en obtenir un nouveau.

Conséquence : un ancien administrateur possédant ses jetons peut conserver ses autorisations malgré sa rétrogradation ; changer le mot de passe ne coupe pas une session volée. Le renouvellement répété permet de prolonger cette situation.

Correction : sessions de renouvellement stockées sous forme de hash, rotation avec invalidation de l'ancien jeton, révocation et vérification de l'existence/du rôle courant. Prévoir une stratégie d'invalidation des jetons d'accès pour les changements sensibles.

### 4. P2 — Validation absente lors de la modification d'un aquarium

Preuve : `back_end/src/aquariums/aquariums.controller.ts:38`.

`Partial<CreateAquariumDto>` est un type TypeScript effacé à l'exécution. Le ValidationPipe reçoit Object et n'applique pas les contraintes du DTO. Vérification locale : `{ lengthCm: -10, unexpected: 'accepted' }` traverse le pipe sans erreur.

Conséquence : dimensions négatives et valeurs invalides atteignent le service ; certaines peuvent être enregistrées, d'autres provoquer une erreur serveur. Les propriétés inconnues ne sont pas toutes persistées, car le service construit explicitement son patch.

Correction : classe `UpdateAquariumDto extends PartialType(CreateAquariumDto)` et tests HTTP pour valeurs négatives, dates invalides et types incorrects.

### 5. P2 — Modification de l'email sans nouvelle vérification

Preuve : `back_end/src/users/users.service.ts:139-158`.

Le nouvel email est enregistré immédiatement tout en conservant `emailVerifiedAt`. Aucune confirmation de possession de la nouvelle adresse n'est exigée.

Conséquence : un compte reste marqué vérifié avec une adresse non vérifiée ; une faute de saisie peut transférer la récupération du mot de passe à une mauvaise boîte mail.

Correction : conserver un email en attente, envoyer un lien de validation et n'appliquer le changement qu'après confirmation ; demander une réauthentification pour cette opération sensible.

### 6. P2 — Inscription bloquée après échec ou expiration de l'email

Preuve : `back_end/src/auth/auth.service.ts:47-58` et routes de `auth.controller.ts`.

L'utilisateur est enregistré avant l'envoi SMTP. Si cet envoi échoue, l'inscription retourne une erreur mais le compte existe déjà. Une seconde inscription rencontre un conflit et le login refuse un compte non vérifié. Aucun endpoint de renvoi de vérification n'a été trouvé. Un lien expiré produit le même blocage sans intervention.

Correction : prévoir un renvoi limité en fréquence avec réponse non révélatrice, une reprise des inscriptions non vérifiées et une gestion fiable des tentatives d'envoi.

### 7. P2 — Déploiement sans application des migrations

Preuve : `.github/workflows/cd-deploy.yml:33-40`, `back_end/src/config/typeorm.config.ts:20`, dossier `back_end/migrations`.

Le workflow reconstruit et redémarre les conteneurs sans exécuter les migrations SQL. La synchronisation automatique est désactivée en production, ce qui est une bonne protection, mais aucun mécanisme versionné ne la remplace dans le déploiement fourni.

Conséquence : si les migrations n'ont pas été passées manuellement, le nouveau code peut démarrer contre un ancien schéma, notamment pour les ajouts PayPal et les rappels. L'état réel de la base serveur n'a pas été inspecté.

Correction : runner de migrations avec historique, étape explicite avant activation, sauvegarde et contrôle HTTP de santé après redémarrage. Déployer un commit identifié et validé par la CI, plutôt que simplement le dernier main au moment du pull.

### 8. P2 — Tutoriel automatique non déclenché après connexion

Preuve : `front_end/web/src/app/core/auth.service.ts:9` et `:143`, `back_end/src/users/users.controller.ts:18-23`, `back_end/src/users/user.entity.ts:22`.

Le backend renvoie `id`, alors que le type frontend Me et `fetchMe()` attendent `userId`. L'appel devient `offerForUser(NaN)` ; le service de tutoriel rejette ce paramètre avec `Number.isInteger`.

Correction : aligner le contrat API sur `id` ou ajouter un mapping explicite ; tester le premier login avec une réponse `/users/me` conforme au backend.

## Qualité et maintenance

- Points positifs : mots de passe Argon2, tokens de vérification stockés sous forme de hash, refresh cookie HttpOnly/SameSite strict, guards globaux de rôle et de plan, limites de fréquence sur plusieurs routes sensibles, requêtes paramétrées dans les portions inspectées et synchronisation TypeORM désactivée en production.
- Les tests existants passent, mais les tests dits fonctionnels d'authentification appellent directement le contrôleur avec JWT et utilisateurs simulés. Ils ne vérifient pas la chaîne HTTP réelle des guards et du ValidationPipe, ce qui explique que les défauts ci-dessus puissent leur échapper. Ajouter en priorité des tests d'intégration ciblés sur ces frontières.
- Trois feuilles de style dépassent leur budget de 20 kB : aquarium-detail 44,97 kB, admin-users 21,27 kB, admin-metrics 28,88 kB. Ce sont des avertissements de build, pas une preuve de lenteur mesurée. Mutualiser les styles et mesurer avant toute optimisation plus large.
- Le README racine est encore celui du starter Nest et propose des commandes absentes du package racine. Documenter les deux applications, les variables, le schéma initial, les migrations, les tests, le déploiement et la restauration.
- La CI frontend de tests ne se déclenche que sur un push vers main ; aucun événement pull_request n'apparaît dans les workflows inspectés. Exécuter les contrôles avant intégration et standardiser `npm ci`.

## Ordre recommandé

1. Contrôles de propriété poissons/plantes et tests avec deux comptes.
2. Séparation des jetons, révocation des sessions et actualisation des rôles.
3. DTO runtime et sécurisation des changements/validations d'email.
4. Migrations intégrées au déploiement et tests d'intégration HTTP.
5. Contrat utilisateur du tutoriel, documentation et budgets CSS.
